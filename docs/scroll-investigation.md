# 自動スクロールの調査

## 確認範囲

調査対象は現行の v1.5 `content.js` です。過去バージョンの比較や、報告された実サイト上の再現は行っていません。
したがって実際の症状を単一の原因に断定せず、コード上の問題と合成ページで再現した不具合を分けています。

## 旧実装の問題

1. **更新処理が実行されない経路**
   `MutationObserver`、画像 load、resize、遷移後の予約はすべて `scheduleUpdate()` へ集まります。
   毎回 `updateTimer` を取り消す trailing debounce なので、100ms未満の間隔でDOM更新が続くと `update()` が永久に延期されます。
   `navStart + 2500` の期限は `update()` の内部にしかなく、この経路には効きません。
   20msごとにclassを変えるページで未スクロールになることを旧コードで再現しました。
   このテスト単独は「ズームだけが成功する」という報告全体の再現ではありません。

2. **完了状態とタイマーが一対一でない**
   `update()` は `pendingScroll` がtrueの間、既に検証中でも別の `performScroll()` を予約できます。
   各実行が独立した8回の検証チェーンを作り、共通の `verifyTimer` には最後のハンドルしか残りません。
   同じ遷移内でも共有の `pendingScroll` を別チェーンが終了させ、遷移時の取り消しも全チェーンを保証できません。
   古い検証の `id !== navigationId` 分岐も共有の `pendingScroll=false` を実行します。
   画像が見つからない検証は `return` するだけで次の検証を予約しません。
   一方、全チェーンが終了した後の位置復元は監視されず、ズームだけは更新されてもスクロールは再開しません。
   競合を起こすテストで、旧コードのスクロール命令が新しい有限期間を超えて継続することを確認しました。
   これだけで旧コードが必ず無限ループするとまでは言えません。

3. **入力と自動スクロールの混同**
   `programmaticScroll` の80ms間は、実際のwheel、touchmove、スクロールキーを無視します。
   自動スクロール自体はこれらの入力イベントを発生させないので、この抑止は不要です。
   命令直後に入力して位置を動かすテストで、旧コードは後から画像上端へ戻しました。
   またSPA遷移の350msポーリング前に入力すると、古い遷移の `userScrolled` を設定した後、
   `startNavigation()` がfalseに戻します。この順序でも手動位置が上書きされることを再現しました。
   スクロールバー操作の入力検知はありませんでした。

4. **ページのライフサイクルと復元**
   旧 `pageshow` は同じURLなら状態を初期化しません。
   完了後に同じドキュメントがBFCacheから戻る場合、以前の終了状態が残ります。
   終了後に `pageshow(persisted=true)` を合成するテストで再現しました。
   実際のBFCache経由の往復を再現したテストではありません。
   通常ロードでも `load` / `pageshow` と位置復元が遅れる可能性を考慮しています。
   `history.scrollRestoration` は読み取ってログに残しますが、サイトの復元機能を無効にはしません。

5. **window以外のスクロール**
   `scrollIntoView` 自体は祖先のスクロール領域も動かせます。
   しかし旧検証は画像の画面座標だけを0と比較するため、内部領域の境界、CSSのオフセット、
   スクロール範囲の上限で止まっているケースを区別できません。
   内部領域での動作と、内部位置をサイトが戻した後の復帰をテストしました。

## 修正

- `waiting → recovering → done` と `cancelled` の状態を導入。
  遷移ごとにスクロール予約・animation frame・終了期限を一組だけ所有し、遷移と手動入力で取り消します。
- 更新イベントは最初の100ms予約を維持し、連続イベントが実行を延期しないようにしました。
  初回スクロール予約も後続の更新で延期しません。
- 画像の探索条件とズームの数式・範囲は維持しました。
  自分のbody zoom変更を無視する判定は、他のbody style変更まで無視しないよう補強しています。
- 最初の補正処理から2秒だけ、captureでwindowと内部領域のscrollイベントを監視して補正します。
  命令直後も検証しますが、配置済みなら次の検証を自発的には予約しません。
  位置が変わり続けても期限は延長しません。
- `scrollIntoView` を維持し、祖先領域ごとの位置・残りスクロール範囲・ズームを含むCSSのオフセットから補正要否を判断します。
- 手動入力は直ちにキャンセルします。入力処理の前にURL変更も検査します。
  入力欄の編集キーはページスクロール操作として扱いません。
  通常クリックはキャンセルせず、検知できるスクロールバーのgutter操作はキャンセルします。
- BFCacheの `pageshow` は新しい遷移として扱います。
  通常の遅い `pageshow` も初回だけ、既に終了していて手動キャンセルされていなければ再開します。
  単にタイマーを長くする方式にはしていません。
- 任意有効化の診断ログで、未実行、命令直後、後からの変化、キャンセル、期限終了を区別します。
  ログの具体的な使い方はREADMEに記載しています。

## 検証と残る限界

`tests/test_browser.py` は実Chromiumでコンテンツスクリプトを直接実行します。
最大画像・ズーム・リサイズ・SPA、連続Mutation、遅延画像、位置上書き、内部領域、
即時入力、SPA検知前の入力、有限期間、合成pageshow/BFCache、CSSオフセットを検証します。
命令後にサイトがページ先頭へ戻すテストと、位置を繰り返し戻すテストを分けています。

Chrome自身の復元処理とサイトの `scrollTo` はscrollイベントからは区別できません。
診断ログで位置の変化時点を確認したうえで、必要なら実サイトのPerformance記録を調べる必要があります。
終了期限後に毎回位置を戻すサイトへ無期限に対抗することは避けています。
画像が一度配置された後、期間外に別の最大画像が追加された場合も、自動スクロールは再開しません。
ネイティブUIがページへ入力イベントを送らない場合、手動スクロールバー操作の完全な識別はできません。

manifestの仮URLと管理ブラウザーの拡張読み込み禁止は別の既存制約です。
それらを変更・回避せずテストしているため、拡張としての実サイト上の動作確認は未実施です。

実行結果（Chromium 154 / Playwright 1.62.0）:

- `node --check content.js`: 成功。
- `python3 -m unittest discover -s tests -v`: 13件実行、13件成功、スキップなし（36.181秒）。
- 旧コードに対しても同じテスト群のうち11件を実行し、連続Mutation、命令直後の入力、SPA検知前の入力、完了後のBFCache相当イベントなどで失敗を確認しました。ログを前提にする検証の失敗は、動作上の再現とは区別しています。
- `git diff --check`: 成功。
